# MCAC Formal Specification and TypeScript Mapping

## Source

Source manuscript: **Multi-Context Access Control Framework**, `complete_research_paper.pdf` at the repository root (17 pages). Sections VIII–XIII and Appendix A were read; the equations and tables were present in text extraction. The path `docs/research/MCAC-research-paper.pdf` mentioned in the request does not exist in this checkout. The supplied root PDF is the source used here.

The policy model is score-free. All severities are from `{0,1,2}`; there is no numeric risk score or weighted combination.

## Clarifications requested

1. **Γ naming/example conflict:** Section IX-B calls the mechanism cross-category consistency, but its example joins device and network class, both members of `Ce` under Eq. (3). The engine accepts declared Γ constraints over any items and applies their recorded outcomes; please confirm whether a constraint must actually span `Ce` and `Cb`.
2. **Missing `Θ` entry:** Section IX-B defines `Θ[xn]` and says degraded network makes a condition I, but does not define a valid network class absent from a finite threshold table. The engine raises a configuration error on that branch. Please confirm whether it should be I, use a default, or make the policy invalid.
3. **Waiver expiry endpoint:** Eq. (12) specifies a waiver duration but does not state whether the exact expiry instant remains valid. The implementation uses a half-open interval, matching the existing app’s strict `expires_at > timestamp` check. Please confirm if that boundary should be different.
4. **Comparator grammar:** Eq. (5) leaves `⊕` abstract; Section XII-D/Section XI-B show examples but no exhaustive operator grammar. The engine implements the cited operators plus typed scalar comparisons. Please confirm the complete policy comparator set before wiring the existing policy editor.

These do not block the independent Eq. (1)–(11) mechanics, traces, versioning, or tests. Unknown table mappings and invalid operator shapes are rejected instead of being assigned an invented meaning.

Phase 1.1 has a separate source-by-source ambiguity analysis in [mcac-author-decisions.md](mcac-author-decisions.md), plus the full conformance ledger in [mcac-conformance-audit.md](mcac-conformance-audit.md). Independent evaluator code is at `lib/mcac/reference/equation-19.ts`; its limited scope is documented in that audit.

## Algorithm 1 mapped pseudocode

```text
DECIDE(request q, immutable policy P, explicit context items, Γ outcomes, waiver result):
  create trace using q and P.version
  if BP(q.user, q.resource, q.action) = 0:
    record DENY with baseline=false; return
  select class profile and rules applicable to class/action
  validate explicit items; apply enabled Γ outcomes (involved status can only become X)
  classify every item with Eq. (2), in its stated precedence
  mEnv = 0; mBeh = 0
  for each applicable rule and each condition in its two categories:
    compute ε using Eq. (5); compute g using Eq. (7)
    if supplied waiver is valid and g = 1: set g = 0 using Eq. (12)
    record referenced item/status, ε, strength, effective g, and interaction evidence
    update that category severity using max
  m = max(mEnv, mBeh)
  map (BP, m, ψ) using Eq. (11); an attempted invalid verification yields DENY
  append canonical SHA-256 chained trace; return decision and trace
```

Implementation: `lib/mcac/decision.ts:evaluateMcac`, `lib/mcac/conditions.ts`, `lib/mcac/interactions.ts`, `lib/mcac/severity.ts`, and `lib/mcac/trace.ts`. The trace uses explicit request timestamps and caller-supplied chain head; no wall-clock or database read occurs in this procedure.
