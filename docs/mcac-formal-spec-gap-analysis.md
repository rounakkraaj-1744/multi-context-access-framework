# MCAC Formal Specification Gap Analysis

**Scope:** Read-only analysis of the authoritative paper PDF and current repository implementation. No application code, schema, policy types, evaluator behavior, or paper files were changed for this report.

**Snapshot note:** This report records the gap analysis before the Γ/Θ decisions in the current task were approved. Its original statements that Γ scope and Θ totality were unresolved are superseded by [the approved-semantics addendum](mcac-formal-semantics.md); its inventory of remaining comparator-grammar gaps remains relevant. The current PDF in the workspace is 19 pages; see [the manuscript-alignment report](mcac-manuscript-alignment.md) for findings against that version. The historical audit body below has not been retroactively rewritten.

## 1. Executive summary

The current evaluator has a finite comparator implementation, a concrete but externally supplied Γ outcome interface, and a concrete network-keyed Θ lookup. Those implementation choices do not fully follow from the paper. The paper defines the condition operator abstractly as ⊕; it does not specify an exhaustive operator grammar or operand typing. It describes Γ as consistency constraints that can degrade involved context items, but neither gives executable predicates nor resolves the meaning of “cross-category” when its device/network example uses two environmental items. It defines Θ lookup when the network item is degraded, but not the result when the network is valid and no corresponding key exists.

Consequently, a draft can be checked for conformance to current code shape, but a policy containing conditions, Γ constraints, or network-conditioned thresholds cannot be fully validated as conforming to the paper until the unresolved semantics are decided. The draft readiness gate in docs/mcac-policy-lifecycle.md correctly keeps publication blocked. This report does not recommend silently treating implementation behavior as research semantics.

At the time this historical audit was written, the only authoritative paper source found was complete_research_paper.pdf. No editable manuscript source was found; the .tex files in research-evaluation/paper-tables/ are table fragments, not the paper source.

## 2. Comparator inventory and semantics

The paper introduces a condition as κ=(k,⊕,θ,s) and defines Eq. (5) in terms of whether x_k ⊕ θ holds (Section VIII-D, PDF p. 6). It gives examples in the policy fragment and worked examples (Section XII-D, PDF p. 9), plus history and navigation definitions (Section XI-B, PDF p. 7) and a device-evidence rule (Section XI-C, PDF p. 7). It does not enumerate a complete ⊕ grammar, define general operand typing, or specify invalid-operand behavior.

The TypeScript union is lib/mcac/types.ts:Comparator (line 50). An operator present in the union but not seen in current fixtures is still an implementation capability, not a paper-approved operator.

### Comparator-wide observations

- A degraded referenced item yields I before compare is called (conditions.ts:16–19). A valid item with a comparison that evaluates false yields F; the evaluator does not distinguish predicate false from several comparator-level malformed shapes that fall through to false.
- The runtime policy validator is stricter for selected operators (registered, numeric, in, in_window, not_novel, expected_transition) but allows broad eq/neq operands. It is not a complete JSON policy validator. See decision.ts:validateCondition.
- The paper says rules are conjunctive and disjunction may use set membership or separate resource classes (Section VIII-D, PDF p. 6). It does not specify the operator-kind matrix the implementation enforces.
- Current tests concentrate on gte, lte, in_window, not_novel, expected_transition, and Γ/Θ cases. eq, in, and numeric lt/gt have no direct behavior tests in lib/mcac/mcac.test.ts; registered also lacks a direct condition-evaluation test. The decision gate does not establish paper conformance for untested operators.
- lib/mcac/reference/equation-19.ts:evaluateReference intentionally rejects ambiguous policy shapes; its header describes it as covering the “unambiguous core.” Its selected differential tests are not an exhaustive comparator oracle (mcac.test.ts:152–164).

## 3. Γ consistency analysis

### Exact code contract

- PolicyVersion.consistencyConstraints is an array of DeclaredConsistencyConstraint, whose exact shape is { id: string; items: readonly ContextItemKind[] } (lib/mcac/types.ts:68–70, 79). It contains no predicate, expected relation, value, function, or data-source reference.
- Outcomes are supplied separately as { id: string; violated: boolean } (ConsistencyEvidence in types.ts:70). AuthorizationInput requires a consistencyEvidence array (types.ts, input contract near lines 135–153).
- decision.ts:validateModelPolicy checks duplicate/declared IDs and that each declared constraint has a non-empty, duplicate-free items list. It validates supplied evidence IDs, duplicate evidence IDs, and the Boolean violated field. It does not compute whether a constraint is violated or fully runtime-check that item names are valid members of ContextItemKind.
- interactions.ts:evaluateCrossCategoryConsistency maps evidence by ID. For each declared constraint, if the switch is disabled it records DISABLED and does not require outcome evidence. If enabled and evidence is missing, it throws. If evidence says false, it records NOT_VIOLATED; if true, it records APPLIED and returns all listed item kinds as contradicted. decision.ts passes that set to classifyContext.
- context.ts:classifyValidity checks M, then required-integrity U, then contradiction X, then stale S, then valid V. Thus contradiction does not override missing or unverifiable status. This order matches the paper’s Eq. (2), Section VIII-B, PDF p. 6.

### Paper statements versus missing predicate semantics

**Explicit in the paper:** Γ is a set of declared consistency constraints over context items (Section VIII-B, PDF p. 6). Section IX-B, PDF p. 7 says a violated constraint sets involved item statuses to X, constraints can only degrade status, and gives an example involving a registered device and a network class “never previously associated with that user.”

**Unspecified:** The paper does not define a predicate language or evaluation function for γ; how the “never previously associated” relation is stored, scoped, enrolled, or evaluated; what evidence proves satisfied/violated; whether predicates may be supplied by a PIP, policy compiler, or another trusted component; or what decision/status applies if Γ evidence is unavailable. The implementation does not answer these questions: the caller supplies the Boolean result.

**Scope conflict:** The paper calls Γ “cross-category” and says constraints may relate items across categories, but its example joins device and network. Under the paper’s own partition in Eq. (3), both are environmental (C_e) items. The type permits any non-empty item subset, including one item or same-category combinations, and the implementation accepts them. Whether Γ must span environmental and behavioral categories is an author decision, recorded in docs/mcac-author-decisions.md:7–19.

### Confirmed behavior versus assumptions

Confirmed by code: explicitly supplied true evidence changes only listed items to X; false evidence does not degrade them; enabled constraints without evidence throw; disabled constraints do not consume evidence; and a constraint can currently mention same-category items. Confirmed by tests: satisfied/violated/disabled outcomes and that only involved items become X (lib/mcac/mcac.test.ts:182–201).

Not established: that the supplied Boolean is truthful, that a defined real constraint predicate was run, that the code’s arbitrary-scope behavior is the intended Γ semantics, or that missing Γ evidence should throw rather than become I, a configuration error, or another specified result. These are not inferred here.

## 4. Θ threshold analysis

### Exact code contract

- Threshold is either ThresholdValue or { by: "network"; values: Readonly<Record<string, ThresholdValue>> } (lib/mcac/types.ts:25–26, 50–57). ThresholdValue permits strings, numbers, Booleans, arrays of those primitives, or a startHour/endHour/optional-weekdays object.
- conditions.ts:evaluateCondition calls resolveEnvironmentConditionedThreshold for behavioral conditions. interactions.ts:isNetworkThreshold identifies an object with a by property as a network lookup; runtime validation later requires by === "network" and only permits it for a behavioral numeric comparison.
- decision.ts:validateCondition requires each value in a network lookup table to be a number, but does not require keys to match recognized network classes, require all classes to be present, or check that the numbers are finite.
- Recognized runtime network values are exactly corporate, vpn, known, and unknown (ContextValueMap in types.ts:16; also guarded in context.ts:validValue).
- When the interaction is enabled and network status is degraded or missing, the resolver returns undefined; evaluateCondition then returns I. The interaction is recorded as INDETERMINATE. When enabled and the valid network value is present in the map, its numeric threshold is selected and the interaction is APPLIED. When valid network has no key, the resolver throws (interactions.ts:6–19).
- When the interaction switch is disabled, the resolver returns undefined and records DISABLED; the condition still evaluates to I because it has no parameter. It does not substitute a constant threshold. A separate constant-threshold policy is needed to evaluate the no-interaction case.

### Paper status and gaps

Section IX-B, PDF p. 7, explicitly defines θ=Θ[x_n] for a finite table and says degraded c_n makes the condition outcome I. It does not specify the valid-but-unlisted key branch, nor require Θ to be total over Table VI’s network domain. The worked policy (Section XII-D, PDF p. 9) includes corp, vpn, and known, but not unknown.

Therefore current behavior is only partly specified: degraded network handling is explicit and tested (mcac.test.ts:166–180); valid network with missing key is a runtime configuration exception, not a paper-defined decision. The behavior when interaction is disabled is a code-level representation and is not an explicit paper-defined output rule.

### Key-name inconsistency

The paper’s Table VI (PDF p. 9) uses corporate, VPN, known, unknown while its simplified policy and Example 4 use corp. The TypeScript context union and tests use lowercase corporate, vpn, known, unknown. No paper passage declares corp an alias for corporate, nor specifies case normalization. The current evaluator does exact string lookup, so corp and corporate differ. Policy validation does not reject unsupported keys or aliases; an unrecognized key is simply unreachable from a validated context value, while a missing recognized key throws at evaluation.

## 5. Paper/code/test inconsistencies and other gaps

1. **Comparator inventory is not paper-closed.** types.ts:Comparator exposes eleven operators, while the paper uses abstract ⊕ and illustrates a subset. docs/mcac-author-decisions.md:48–60 correctly marks exhaustive grammar as requiring an author decision. Code support is not proof that all eleven belong to the formal model.
2. **Comparator operand semantics are unevenly checked.** validateCondition enforces selected item/operator pairs and parameter kinds but does not establish a complete operator × item × operand table. eq/neq are unrestricted; in only checks array-ness; numeric validation accepts negative numbers; in_window does not constrain hour ranges to a day. Tests do not cover all these cases.
3. **Paper network labels vary.** Table VI says corporate; the example uses corp. Runtime uses only corporate. No alias semantics are specified.
4. **Γ prose says cross-category, example is same-category under the paper’s partition.** Code accepts arbitrary item lists. Tests use device+network, preserving the same-category example rather than resolving the conflict (mcac.test.ts:182–201).
5. **Γ detection is outside the evaluator.** The paper’s Algorithm 1 says APPLYCONSTRAINTS(C_e,C_b,Γ) (PDF p. 10), but production evaluateCrossCategoryConsistency only consumes an ID/Boolean result. It does not implement constraint predicates. The trace records evidence but cannot prove how it was derived.
6. **Γ missing-evidence behavior is a throw.** This is a fail-closed implementation error, but the paper does not specify the operational behavior for an unavailable constraint evaluator.
7. **Θ missing-key behavior is a throw.** Test asserts the throw for unknown with a table that only contains corporate/VPN (mcac.test.ts:179–180); the paper does not define a throw or authorization result.
8. **The Θ type permits broad values but evaluator narrows at runtime.** Shared ThresholdValue includes non-numeric forms, while validateCondition rejects non-number values for a network lookup. This is not itself a paper contradiction, but shows the type is broader than the evaluator’s actual Θ contract.
9. **Θ and disabled interaction behavior are distinct.** A policy that sets environmentConditionedThresholds false while retaining a network map yields an indeterminate comparison, not a constant threshold. The harness’s B6 no-interaction system builds a distinct policy; toggling the interaction alone is not equivalent to substituting a fixed threshold (lib/mcac/experiment/harness.ts, makePolicy/B6 evaluator).
10. **Tested behavior is selected, not exhaustive.** mcac.test.ts checks selected comparator cases, Γ outcomes, and Θ selection/degraded/missing-key paths. It does not establish full paper conformance, and the independent reference evaluator explicitly blocks ambiguous shapes (lib/mcac/reference/equation-19.ts).
11. **Policy types do not encode all publication scope.** PolicyVersion profiles are indexed by resource class, and each rule has a resource class plus actions, but there is no top-level exact policy scope or active-version selector. docs/mcac-policy-lifecycle.md identifies this binding gap.

## 7. Explicit unresolved research decisions

These questions must be answered by the paper authors or an approved specification authority; implementation should not choose for them.

1. **Comparator closure:** Is ⊕ exactly the eleven operators currently represented in types.ts, or a smaller/larger formal set? Define each operator’s admissible item kinds, parameter type, structured equality/membership semantics, and invalid-type behavior.
2. **Comparator edge semantics:** Define range endpoints, hours domain and equal-window behavior for in_window; define numeric comparison domains/units; decide whether negative thresholds are valid; specify how absent history entries and missing navigation predecessor are treated when the item itself is otherwise V.
3. **Network vocabulary:** Is the network class corporate or corp? Are aliases or case normalization allowed? Reconcile Table VI and the policy example.
4. **Γ scope:** Must each constraint span C_e and C_b, or may it relate same-category items? Resolve the device/network example or revise it.
5. **Γ predicate semantics:** What exactly constitutes violation for each declared constraint? How is per-user “never previously associated” evidence computed, over what enrollment/window, and which trusted component produces it?
6. **Γ unavailability:** If a constraint cannot be evaluated, is its outcome indeterminate, a policy/configuration error, or another specified result? The current type has only Boolean evidence and cannot directly represent unavailable.
7. **Θ missing key:** For valid network evidence with no table entry, should validation reject the policy, condition evaluation return I, or use an explicitly defined default? Should every table cover every recognized network class, including unknown?
8. **Interaction disabled semantics:** If Θ interaction is disabled, is a dynamic Θ condition invalid, indeterminate, or transformed by an explicitly authored constant threshold? If Γ is disabled while Γ declarations remain, should those declarations be ignored or make the policy invalid?
9. **Waiver endpoint:** Is validity half-open or closed at expiresAt? This affects exact expiration-time decisions and policy validation/replay.

The first four are already recorded in docs/mcac-author-decisions.md; this report adds the detailed per-operator and interaction-disabled questions exposed by current code inspection.

## 8. Recommended decision sequence

1. **Resolve policy vocabulary and scope first:** action/resource-class binding, canonical network class strings, comparator closure, Γ category scope, and Θ missing-key semantics.
2. **Specify the operator and interaction contracts:** publish typed operator × item × operand rules; define invalid operands and exact boundaries; define Γ predicate/evidence production and unavailable behavior; define disabled-interaction behavior.
3. **Update the authoritative paper/specification through its normal authorship process.** Keep code behavior labeled as implementation until the paper or approved formal addendum records the decision.
4. **Implement a standalone exhaustive validator** against the approved contract. It should reject unresolved, malformed, out-of-scope, incomplete, or internally inconsistent policies before they can become VALIDATED.
5. **Add tests against the decisions:** table-driven comparator tests; Γ scope/predicate/provenance/unavailability tests; Θ full/partial/invalid-key tests; validation rejection tests. Keep independent reference evaluation independent of production helpers.
6. **Only then implement publication and activation:** publish an immutable snapshot, bind it to exact scope, activate atomically with concurrency protection, and make no-active selection fail explicitly. Preserve legacy policies without conversion or fallback.
7. **Prove lifecycle/replay behavior with route and persistence tests** before considering Phase 1B integration. Historical decisions must continue to use the exact archived version recorded in their trace.
